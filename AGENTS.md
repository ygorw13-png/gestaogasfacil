# Architecture rules

- G0.1 release candidates live under `g0.1/candidate/`, outside active `src/` and `supabase/`, because this project's backend is shared with production and managed functions deploy automatically. Do not promote candidates without explicit production approval.
- G0.1 tests use only fictional fixtures and a disposable loopback PostgreSQL cluster; never use the production client or operational records as fixtures.
- Candidate authentication uses one session coordinator for initialization, refresh, manual login and events, because generation checks must precede accepting session identity and duplicate verification must share its result.
- G1 backend candidates (SQL) live under `g1/candidate/sql/` and are applied only to the disposable loopback cluster (`g1/tests/sql/setup_cluster.sh`); production contingency is a containment file that keeps the security blocks, never a rollback that reopens them (rollbacks are lab-only), because the Cloud backend is shared with production.
- Controlled actions (delivery transitions, cargo, receipts, admin corrections) are SECURITY DEFINER RPCs that take an idempotency key and lock the affected row; direct table writes are blocked by triggers unless `g1.acao_controlada` is set inside such an RPC.
- Order value reads go through `src/lib/orderMetrics.ts` (`orders.price` is the sale total, never multiplied by quantity), so dashboard, reports and cashier agree.
- `HANDOFF_CLAUDE.md` is the single current-state document (published/preview/candidate/pending, decisions, commands, Cloud-only resources); update it when that state changes, because older reports are historical.
- Screens call G1 controlled actions only through `src/lib/g1/acoes.ts`, gated by `G1_ACOES` (on by default since the Cloud database received 001–010; `VITE_G1_ACOES=off` disables it), so screens and database switch together; offline-queued actions must carry their idempotency key in the payload.
- Operational date is `America/Bahia`: SQL uses `public.data_operacional()` (candidate 006) and screens use `src/lib/dataOperacional.ts` / `hojePortaria()`, because the Cloud database runs in UTC and movements between 21:00 and 23:59 used to fall on the next day.
- Screen operations that write money or stock use `useOperacaoUnica` (`src/hooks/useOperacaoUnica.ts`, key helpers in `src/lib/g1/operacao.ts`): the idempotency key is bound to the operation content, kept after an uncertain failure and never silently reused for different content; the SQL side stores a content hash with the key (candidate 005).
- Candidate SQL files are numbered in application order (`g1/candidate/sql/00N_*.sql`); check existing numbers before adding one, and add a `reset_com00N.sh` + `run_*.py` suite for it.
- `docs/CHECKLIST_UNICO.md` is the single checklist (implemented / tested / pending / published); update it with each batch.
- Completed sales are never cancelled or rewritten: cancel/return/exchange/duplicate go through the reversal RPCs (`reversao_*`, `reembolso_registrar`, `conferencia_resolver`, candidate 011) that record authorization, physical facts and refunds separately, because history and closed days must stay intact.
- Deliveries are orders with `origem_venda` 'pedido'/'online'; their date is `entrega_prevista` or the Bahia creation day; a total cash closing is refused in SQL (trigger + advisory lock shared with order writes) while any such delivery dated on or before the closing day is open, with no age limit (candidate 013), because a screen-only check can be bypassed.
- On phones (<640px) any shadcn `Table` wider than its container switches itself to cards (labels from the header, `components/ui/table.tsx` + `index.css`); add `data-sem-cartoes` to a table to opt out, so new listings stay usable on mobile without per-page card code.
- Payment methods are stored as canonical codes defined once in `src/lib/formasPagamento.ts` and mirrored by `public._forma_pedido` (candidate 014); unknown methods raise errors and optional-value methods store NULL price, because silent fallbacks turned Gás do Povo into Convênio/promissória.
- Delivery push uses its own service worker scope (`/push/`, `public/push-sw.js`) separate from the offline `sw.js`, and `send-push` reads the recipient from the order in the database, because a shared scope made the workers replace each other and client-supplied recipients allowed misdirected alerts.
- Changing the payment method of a completed sale goes only through `admin_corrigir_forma_pagamento` (candidate 015): admin + reason + idempotency key, never touches price/stock, and cancels only the promissory note proven to be created with the sale (same order_id, same created_at, same value, fully open); anything else is refused for reconciliation, because titles must never be matched by name or value.
- Assigning/reassigning a delivery goes through `atribuir_entrega_aviso` / `reatribuir_entrega_aviso` (candidate 016) with a mandatory channel (App + WhatsApp; Só WhatsApp refused until inbound replies exist), the driver phone comes only from `colaboradores.user_id` (explicit link, admin-only) and the WhatsApp request is queued in `whatsapp_envios` in the same transaction; `whatsapp-envio` sends it server-side via the official connector and records enviado/falha/incerto (no blind resend), because name matching and wa.me links sent alerts to the wrong person or not at all.
- WhatsApp by QR code (optional, no Facebook) goes only through `whatsapp-qr` + `_shared/whatsapp-qr-core.ts` against an external, always-on Evolution API v2 server read from server secrets (`EVOLUTION_API_URL` https, `EVOLUTION_API_KEY`), one instance per organization named server-side, admin-only; it never sends messages nor touches `whatsapp_config`/`whatsapp_envios`, because edge functions cannot hold a WhatsApp Web session and client-supplied URLs would allow SSRF.
- Agregados (candidate 017): a withdrawal is the order itself (`payment_method='agregado'`, price NULL) written only by `retirada_agregado`; prices live in admin-only `agregado_precos` (`resellers.price_p13` is column-revoked); por conta, acerto, adjustments and credit refunds go only through the `agregado_*` RPCs (admin, idempotency key, per-agregado advisory lock) and the browser never receives prices for non-admins, because agregado prices are confidential and quantities must never be settled twice.
- WhatsApp "Aplicativo do PC" (candidate 018/018c): the Windows app talks only to `whatsapp-desktop` (protocol v1, verify_jwt=false, no CORS because the caller is not a browser), authenticated by a single-use 10-min pairing code or a 256-bit device token, both stored only as sha256 in service-role-only tables; provider is chosen explicitly in `whatsapp_config.provedor`, any provider/phone change turns sending off, envios keep the provider chosen at assignment (no fallback, old Meta rows never move), and a job id is offered once: unstarted reservations expire to `falha`, started ones to `incerto`, resends are manual new rows linked by `reenvio_de`, because the device must never resend blindly or block the queue.
- Driver WhatsApp alerts carry only the order number and an HTTPS link to `/entregador/entregas?pedido=<id>` on the published site (candidate 019); access is enforced by login + the existing orders RLS (active profile, same org, entregador role, current `delivery_person_id`), because alert texts leave the system and must not expose customer data.
